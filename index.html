Security & Hardening Kit

A configurable Bash tool for auditing baseline Linux security posture — SSH, firewall, and fail2ban — built to run unattended, in CI, or ad hoc against any host.

bash 4+ MIT license v0.1.0 tested: debian/ubuntu

Overview

Most security audits are one-off manual checks run before a compliance deadline and then forgotten. This kit is built to be a standing tool instead: config-driven per host, safe to re-run indefinitely because it only reads system state and never modifies it, and scriptable through a machine-readable JSON mode so results can feed a monitoring pipeline or a CI gate rather than requiring someone to read terminal output by hand.

Features

  • SSH root login check (PermitRootLogin in sshd_config)
  • Firewall active check — supports ufw, firewalld, or nftables as the configured backend
  • fail2ban active check via systemctl
  • Dual output modes: human-readable by default, --json for structured output
  • Exit code reflects overall result — 0 if every check passes, 1 if any fails
  • Fully config-driven through YAML — no hardcoded paths or values in the script itself

Installation

cd production-kit-security-hardening
chmod +x scripts/security-audit.sh

Configuration

All tunable behavior lives in config/settings.yaml — nothing is hardcoded in the script itself, so the same script runs unmodified across different hosts and teams.

ssh:
  check_root_login: true

firewall:
  backend: "ufw"   # options: ufw, firewalld, nftables

fail2ban:
  check_enabled: true

Set any check_* flag to false to skip that check entirely on a given host.

Usage

# Human-readable output, for interactive use
./scripts/security-audit.sh

# Structured JSON, for piping into jq or a monitoring pipeline
./scripts/security-audit.sh --json | jq .

# Use the exit code as a CI gate
./scripts/security-audit.sh --json > results.json || echo "Security check failed"

Architecture

config/settings.yaml │ ▼ ┌────────────────┐ each check reads its own │ arg parsing │ config flag, runs independently, │ (--json/--dry) │ and appends one result object └───────┬────────┘ to a shared RESULTS array ▼ ┌─────────────────────────────────────────────┐ │ check_ssh_root_login() │ │ check_firewall_active() │ │ check_fail2ban_active() │ └───────┬───────────────────────────────────────┘ ▼ OVERALL_STATUS = 1 if any check FAILs, else 0 │ ┌─────┴─────┐ ▼ ▼ human lines JSON array (--json) │ │ └─────┬─────┘ ▼ exit $OVERALL_STATUS

Each check function is self-contained and independently skippable via config. Nothing in the checks depends on the invoking shell's environment — the same discipline as deriving SCRIPT_DIR from $0 rather than trusting $HOME, so the tool behaves identically whether run interactively, from cron, or inside a CI runner.

Output & Logging

Human mode prints one line per check:

[FAIL] SSH root login check — PermitRootLogin is set to yes

JSON mode prints a single array, safe to pipe directly into jq:

[{"check":"ssh_root_login","result":"FAIL","detail":"PermitRootLogin is set to yes"}]
Exit codeMeaning
0All enabled checks passed
1At least one enabled check failed

Safety & Failure Handling

The script is read-only against the system — it audits and reports, it never modifies system state, so it is safe to re-run at any frequency. A missing config file, a missing sshd_config, or an absent firewall binary all resolve to a reported FAIL with a specific detail message rather than an unhandled crash, because set -euo pipefail is paired with explicit existence checks before every risky read.

Known Limitations & Extension Ideas

  • Firewall check supports one configured backend per run, not auto-detection across all three
  • Audits and reports only — no remediation/auto-fix mode (a deliberate scope boundary, not an oversight)
  • Extension idea: add a --remediate flag behind an explicit confirmation prompt
  • Extension idea: add a webhook/alert notifier for CI failures
